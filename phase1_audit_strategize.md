# Veto-Pivot Logic in `strategize.rs` (Phase 1 Audit Summary)  The `veto_pivot_strategy` function (line ~1450) is the central dispatcher for critic-driven recovery. It receives the currently active strategy and the `EpistemicSession`. If the session carries a `last_critic_rejected_actions` marker **and** the active strategy maps to a native tool, the function returns a pivot directive of the form `pivot from `<strategy>` to address [CRITIC_VETO] with a different action`. This string replaces the original strategy in the prompt sent to the strategist, forcing the next proposal to choose a different action type.  The admission gate for such pivots is `veto_mandated_pivot_ok` (line ~1500). It first strips read-file bodies from evidence so that literal `[CRITIC_VETO]` tokens appearing inside source code cannot trigger a false veto. It then checks whether the critic's most recent veto text explicitly names the proposed tool (`tool_named`) or its target path (`target_named`). Safe reconnaissance actions (read, search, read-only `execute_command`) are admitted unconditionally when a veto is active. Mutating actions (write, patch, diff) are admitted only when the veto text names the tool or target. The exact rejected action batch is never re-admitted under the pivot exemption.  Two additional veto-aware branches exist upstream in `handle_strategize`:  - **Citation pre-flight** (lines ~380-410): when a mutation task's artifact was vetoed for unverified line citations and no `grep -n` evidence exists, the cortex forces a `grep -n` command across all read targets before allowing another write.  - **Critic artifact-veto recovery** (lines ~430-470): when a just-written artifact was rejected (`[CRITIC_VETO]` or `[HALT_REJECTED]` newer than the last `[WRITE_OK]`), the cortex forces a correction `write_file` instead of re-forcing `halt`.  Together these mechanisms ensure that a critic veto changes the strategist's action type rather than looping the same rejected proposal.
